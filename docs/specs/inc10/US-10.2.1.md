## Descripcion (lenguaje de negocio)

Como **responsable de instalar y operar Cognión**,
quiero **que la versión sea una sola, que se pueda consultar en el sistema en marcha y que cada versión etiquetada traiga su paquete de instalación**,
para **saber qué versión corre en cada máquina y poder instalar una versión concreta sin armar nada a mano**.

---

## Contexto

Hoy la versión aparece en tres lugares sin relación entre sí: `pyproject.toml` (`0.1.0`), `frontend/package.json` (`0.0.0`) y
`FastAPI(version="0.1.0")` en `src/app.py`, mientras el último tag es `v0.10.0`. `/api/health` responde solo
`{"status": "ok"}`, así que no hay forma de saber qué versión está corriendo. El CD publica la imagen en GHCR con el tag
`vX.Y.Z` (con la `v`, que es lo que espera `deploy/gcp/desplegar.sh`) pero no crea una GitHub Release.

`.dockerignore` excluye `*.md` y `docs/` de la imagen; un archivo sin extensión sí se copia. Un test existente
(`tests/unit/inc8/test_us_8_1_6_servidor.py`) exige que `/api/health` sea exactamente `{"status": "ok"}`.

## Especificacion del comportamiento

- **Fuente única:** un archivo `VERSION` en la raíz del repositorio, con el número sin la `v` (`1.0.0`). `pyproject.toml`,
  `frontend/package.json` y la versión de FastAPI **coinciden** con él; una guarda automática falla si no.
- **Se puede consultar:** `GET /api/health` agrega el campo `version` (`{"status": "ok", "version": "1.0.0"}`). El código de
  estado y el campo `status` no cambian, así que el healthcheck de Docker y de Caddy siguen igual. `/api/health/ready` no cambia.
  La imagen incluye el archivo `VERSION`.
- **El tag manda:** el CD **falla** si el tag `vX.Y.Z` no coincide con `VERSION` (evita publicar una imagen `v1.0.0` que diga `0.10.0`).
- **Release en GitHub:** al subir un tag `vX.Y.Z`, el CD crea la GitHub Release con las notas tomadas de la sección de ese número
  en `CHANGELOG.md`, y le adjunta el **paquete de instalación**. La imagen sigue publicándose como `ghcr.io/vvalotto/cognion:vX.Y.Z`
  (con la `v`); no se publica `latest`.
- **Paquete de instalación** (`cognion-X.Y.Z-instalacion.tar.gz`): armado por `scripts/empaquetar_release.sh` a partir de una lista
  de archivos; contiene `VERSION`, `CHANGELOG.md`, la guía de instalación y `deploy/servidor/` (lo agrega `US-10.2.2`, que completa
  la lista). La instalación local sin Docker usa el código fuente de la propia Release (GitHub lo adjunta solo).
- **Versión 1.0.0:** el trabajo de esta US deja el repositorio en `1.0.0` y el `CHANGELOG` con la sección `[1.0.0]` **vacía de
  fecha** (`Unreleased` hasta el cierre del incremento); el tag no se aplica acá, sino en el cierre (`BL-016`).

## Escenarios (BDD)

1. **Versión coherente.** `VERSION`, `pyproject.toml`, `frontend/package.json` y la versión de FastAPI dicen lo mismo.
2. **Guarda.** Si alguno difiere, el test falla indicando cuál.
3. **`/api/health` con versión.** Responde `200` con `status = ok` y `version = <VERSION>`.
4. **`/api/health/ready` intacto.** Sigue respondiendo `base_de_datos`.
5. **La imagen lleva `VERSION`.** El `Dockerfile` copia el archivo y la aplicación lo lee desde ahí.
6. **Paquete reproducible.** `scripts/empaquetar_release.sh X.Y.Z` genera el `.tar.gz` con los archivos de la lista y falla si falta alguno.
7. **El tag manda.** El paso de verificación del CD falla si el tag y `VERSION` difieren.
8. **Notas de la Release.** El extracto de `CHANGELOG.md` para `X.Y.Z` se obtiene con un script probado (sin la sección → falla).

## Fuera de alcance

Mostrar la versión en la interfaz (toca `frontend/`: gate UX); publicar `latest`; cambiar `desplegar.sh`; el contenido de `deploy/servidor/` y de la guía (`US-10.2.2`); aplicar el tag `v1.0.0` (cierre del incremento).

- Hay que actualizar el test que fija el cuerpo de `/api/health`.
- El paso de GitHub Release usa `gh release create` con `contents: write` solo en el job de tags.
